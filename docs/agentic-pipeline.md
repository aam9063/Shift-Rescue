# Agentic development pipeline

I drive [Pi](https://github.com/badlogic/pi-mono) (a coding-agent CLI) through a
custom harness, Gentle AI. Every task starts read-only: I explore, and if the
work is substantial the harness writes a feature document in `odd/tasks/`,
mirrored to persistent memory, *before* the first line of code. Implementation
runs task by task under TDD with exact runners (`uv run pytest`,
`pnpm vitest run`). Anything needing 4+ files mapped, 2+ files written, or
verification commands is delegated to subagents — explore, worker, verify —
each given explicit edit surfaces. Every task closes with one Conventional
work-unit commit on the feature branch, tests and docs alongside the code,
capped near 400 changed lines; oversize work splits into chained PRs. A review
switch runs native review over the commit or PR slice before delivery, and
deterministic findings block. CI then runs lint, strict types, tests and build.
Agents never commit, push, merge or run destructive commands on their own —
those stay my decisions.

**Evidence**: `docs/SHIFT_RESCUE_SPEC.md` §0 (workflow and config),
`odd/tasks/` (25 feature documents), `.atl/skill-registry.md`,
`.github/workflows/ci.yml`.

## The pipeline, step by step

| # | Step | What runs | Evidence in this repo |
|---|---|---|---|
| 0 | **Tooling baseline** | Pi CLI + the Gentle AI harness (persona, workflow, memory, skills, review). Persistent memory via the Engram provider; MCP servers for docs (Context7) and memory. | `.atl/skill-registry.md` (generated by the harness), `odd/tasks/` |
| 1 | **Task arrives → Authorize** | The harness first classifies the request: investigation, explanation, review or proposal stays **read-only**; only an explicit change request may write. Ambiguous intent gets one clarifying question. | `docs/SHIFT_RESCUE_SPEC.md` §0 |
| 2 | **Explore** | Existing code and specs are read before anything is proposed, proportionally to the request. | — |
| 3 | **Resolve uncertainty** | Research only for a named uncertainty; at most one focused question for a real product decision, then stop and wait. Unresolved product choices are recorded rather than guessed. | `docs/assumptions.md` |
| 4 | **Classify** | Two or more meaningful implementation steps (or work worth resuming) makes the task *substantial*; small understood work is done inline with no ceremony. | — |
| 5 | **Track before the first write** | For substantial work: one feature document at `odd/tasks/<feature>.md`, mirrored into persistent memory, plus a visible task list — created before any source edit. Each document carries status, branch, spec references, the problem, decisions that are fixed, an actionable checklist and acceptance criteria. | `odd/tasks/` — 25 documents |
| 6 | **Implement, task by task** | Routing ladder: inline for small/mechanical work; **subagents** beyond it. Delegation fires on the 4-file rule (exploration), the multi-file write rule (implementation), the verification rule (running checks) and the long-session rule. Writers receive explicit *allowed edit surfaces*, never the whole repo. TDD is on: RED observed before implementing, then GREEN and refactor. | `docs/SHIFT_RESCUE_SPEC.md` §0 config table |
| 7 | **Close each task** | One **work-unit commit** on the feature branch with a Conventional Commit message; tests and docs ship with the behaviour, not in a follow-up. The commit identity is recorded in the feature document as evidence. | `git log`, `odd/tasks/*.md` |
| 8 | **Protect the reviewer** | Work is kept near ~400 changed lines per slice; over that it splits into **chained PRs** stacked to the main branch. | `odd/tasks/` delivery notes |
| 9 | **Review** | The review switch runs a native review over the work-unit commit or PR slice — never over the accumulated branch. Only candidate-caused severe findings block; corrections are bounded, and the verdict is issued by the review tooling, not by the author agent. | review records in `odd/tasks/` |
| 10 | **CI gates** | Backend: ruff, mypy (strict), pytest. Frontend: oxlint, vitest, production build. The eval harness (`make eval`, thresholds in `evals/thresholds.yaml`) runs the golden set and the 15 simulated scenarios; the offline parser baseline is informational, real-model runs are the blocking gate. | `.github/workflows/ci.yml`, `Makefile`, `evals/` |
| 11 | **Merge** | A human decision. Push, PR creation and merge are never taken by the agent. | — |
| 12 | **Close and resume** | The session summary is written to persistent memory. Resuming starts by reading the feature document and its memory mirror, reconciling both against the code, and only then continuing. | `odd/tasks/`, memory |

## What I changed from the defaults

Pi ships as a general coding agent; the workflow here is deliberately opinionated:

1. **A harness package over the bare agent.** ODD (Organic Driven Development)
   is the mandatory default workflow for every request; SDD is opt-in only.
   Nothing proceeds on "the model felt like it".
2. **Delegation triggers are mandatory, not advisory.** The 4-file,
   multi-file-write, incident, long-session and verification rules fire on their
   own. Background subagents are enabled.
3. **TDD is switched on with exact runners** (`uv run pytest`,
   `pnpm vitest run`), instead of being left to the agent's judgement.
4. **Work-unit commits with a review-workload ceiling** (~400 lines) and
   chained PRs, rather than one large branch dump.
5. **A review switch over the delivery candidate**, so a commit or PR slice is
   reviewed before delivery instead of relying on CI alone.
6. **Persistent memory wired in.** Feature documents are mirrored outside the
   repo, so an interrupted task resumes from reconciled state rather than from
   a fresh guess.
7. **A generated skill registry.** Skills are scanned from the installed agent
   locations into `.atl/skill-registry.md`; subagents get exact `SKILL.md`
   paths to read, never generated summaries of them.
8. **Hard guardrails.** No autonomous commit, push, merge or destructive git
   operation; writes stay single-threaded unless isolated worktrees are
   explicitly approved.

## What the agents never do

- Commit, push, open a PR or merge on their own. Work-unit commits on the
  feature branch are the one authorized write; the rest is a human decision.
- Run destructive or irreversible operations without explicit approval.
- Write to multiple areas of the repo in parallel.
- Decide business rules. Domain behaviour lives in tested code; the LLM in this
  product interprets language and drafts messages only.

## Honest limits

The harness itself lives outside this repository — it is an installed Pi package
plus user configuration, so what this repo carries are its *artifacts*: the 25
feature documents, the generated skill registry, the ADRs and the spec. The
workflow contract that produces them is quoted in
[`docs/SHIFT_RESCUE_SPEC.md`](SHIFT_RESCUE_SPEC.md) §0, which is the closest
thing to a configuration file that can be linked from here.
